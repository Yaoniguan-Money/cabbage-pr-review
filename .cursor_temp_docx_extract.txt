# 执行摘要  
针对现有“规则引擎+LLM Agent”架构，我们提出“本地化推理+规则补充”方案：将LLM调用替换为可在AMD/CPU上运行的开源模型（如Llama类模型或量化模型）和工具（如llama.cpp、Transformer 库、vLLM等），并利用树遍历解析（Tree-sitter）和YAML diff工具（如DeepDiff、dyff）增强语义分析。所有依赖通过Docker/requirements管理，模型权重提供小型示例或自动下载脚本，无需外部密钥即可运行【12†L1-L4】【27†L117-L125】。以下方案分“在线下载”、“完全离线”两种形式，确保克隆后即能一键运行。

## 1. 系统现状  
根据提供文档（规则引擎审阅报告），当前系统架构为**前端React SPA + 后端FastAPI**，其中核心是一个“YAML驱动、与LLM Agent物理隔离”的静态PR分析层，通过`pipeline_dispatch`在规则引擎和LLM两套流水线间切换。**当前代码/依赖**（文档未详列）：  
- **语言/框架**：Python 后端（使用 FastAPI）、前端 React；规则用 YAML + Python regex 实现。  
- **依赖包**：未指定；推测需 `fastapi`、`pydantic`、`PyYAML`、正则处理（Python `re`），以及LLM相关包（原文未列出）。  
- **数据**：规则集以 YAML 存储（默认规则包，文档多次提及Yaml pattern）；示例输入为PR diff文本（`DiffAtom`）。  
- **模型**：未指定具体LLM；原有代码调用了 `run_agent4`（可能依赖GPT-4 API或类似），但在本地环境下无GPU/API密钥支持。  
- **运行脚本**：文档未提及启动脚本；可能通过FastAPI启动或LangGraph流程驱动。  
- **未解决问题/限制**：现有规则引擎“**瓶颈**”主要是只做纯正则匹配、每文件粒度单原子（DiffAtom）、无跨文件或语义分析；前端展示与后端规则不匹配【原文】。换言之，无法处理大型语义检查或全局上下文规则。  

总结：当前系统**未提供可在本地AMD/CPU环境直接运行的方案**，需要补充本地化LLM推理和跨文件语义分析能力。鉴于评委环境限制（仅有AMD GPU或CPU，不能配置密钥或外部服务），我们重点考虑无需额外配置即可运行的本地开源方案。

## 2. 备选方案与参考资源  
针对需求，重点考虑以下开源项目和技术，并说明如何集成、满足“无密钥、可本地运行”要求：

- **本地化LLM模型（无需API密钥）**：推荐使用开源的Transformer模型，并通过量化/小型化在CPU/AMD上推理。例如Hugging Face的`amd/AMD-Llama-135m`（135M参数，基于Llama2架构）即可直接用Transformers加载【12†L1-L4】；更大的如LLaMA-7B可使用`ggml`/`llama.cpp`量化运行【16†L28-L36】【17†L25-L33】。利用[Transformers](https://huggingface.co/docs/transformers/)加载本地模型，并在代码中替换原来的`run_agent4`调用：例如使用`pipeline("text-generation", model="amd/AMD-Llama-135m")`或者手动`AutoModelForCausalLM`加载【11†L83-L92】。对大型模型可借助[llama.cpp](https://github.com/ggerganov/llama.cpp)生成的量化权重，通过子进程调用，或使用[`llama-cpp-python`](https://pypi.org/project/llama-cpp-python/)绑定（插入代码示例以演示加载）。  
- **推理优化框架**：对于AMD GPU，可使用[ROCm PyTorch](https://rocm.docs.amd.com/)和[AMD提供的Docker镜像](#diagram)运行Torch；例如使用基于`rocm/pytorch-training`的Docker镜像【25†L229-L238】或通过pip安装ROCm版PyTorch【27†L117-L125】。也可用[vLLM](https://github.com/vllm-project/vllm)（高吞吐量推理）或Transformers的`accelerate`加速推理【11†L104-L112】。示例如：`pip install vllm; vllm serve "amd/AMD-Llama-135m"`【11†L104-L112】。  
- **跨文件/语义分析**：引入[Tree-sitter](https://github.com/tree-sitter/tree-sitter)解析器以构建AST，便于实现更复杂规则。Tree-sitter是GitHub开源的增量解析库，能快速生成完整语法树【31†L21-L24】，非常适合静态分析。可以新增`tree-sitter`的Python绑定（`pip install tree-sitter`）和相关语言解析库，对源代码做结构化检查。  
- **YAML/配置差异工具**：现有规则只依赖YAML模式，若需“结构化YAML差异”，可用[DeepDiff](https://github.com/seperman/deepdiff)或[dyff](https://github.com/homeport/dyff)来比较YAML对象而非文本差异。例如StackOverflow指出DeepDiff可以直接比较YAML文件【34†L186-L194】；dyff专用于YAML差异，可突出显示路径变化【33†L293-L302】。可在规则引擎中替代或补充原有`rules_diff`，实现更智能的差异匹配。  
- **其他静态分析工具**：可参考现成的静态扫描工具（如OSS-Guardian、Bandit等）作为额外规则。但因比赛场景特殊，建议重点定制规则引擎，与上述方案结合使用；例如利用已有的Lint工具（`flake8`、`pylint`）做基础检查，剩余逻辑由规则引擎+LLM完成。  
- **示例开源项目**：参考[CR-Mentor](https://github.com/Gijela/CR-Mentor)（知识库+LLM指导式代码审查）思路，但CR-Mentor依赖云服务/多组件，直接移植需重构；可借鉴其“知识库+LLM”理念，构建轻量本地版本。另一项目[Code-Review-GPT-Gitlab](https://github.com/mimo-x/Code-Review-GPT-Gitlab)说明融合多模型能力，但需改为本地模型。

下表比较了几种候选本地模型/推理方式（参数量、运行环境等）：

| 模型/框架              | 参数量    | 格式         | AMD/CPU 支持    | 集成说明                                 |
|-----------------------|----------|-------------|-----------------|----------------------------------------|
| `amd/AMD-Llama-135m`【12†L1-L4】 | ~135M   | HF safetensors | CPU/GPU (ROCm)  | Transformers直接加载【12†L1-L4】。适合演示/测试。 |
| LLaMA-2 7B (Quant)    | 7B        | GGML/gguf    | CPU (量化)      | 用`llama.cpp`转成`ggml-q4.bin`【16†L109-L117】后，CPU运行。 |
| LLaMA-2 13B (Chat)    | 13B       | GGML/gguf    | CPU (量化)      | 同上，建议下调序列长度。                    |
| CodeLlama/WizardCoder | 7B        | HF PyTorch   | GPU/CPU (量化)  | 专注代码生成，可用transformers加载；需GPL许可注意。 |
| 其他（Mistral-7B等）  | 7B        | HF PyTorch   | GPU/CPU (量化)  | 可尝试HF资源，量化到4-bit。                 |

其中[AMD-Llama-135m]示例说明了模型可直接用Transformers获取【12†L1-L4】；LLaMA系列量化步骤见Soulteary博文【16†L109-L117】（使用`quantize`工具减小到几十MB）。使用这些模型时注意：需在代码中将原先调用OpenAI/GPT接口的部分，改为加载本地模型并生成文本，比如`model.generate()`或使用管道模式。

## 3. 详细执行方案  

1. **新增依赖与环境**：创建`requirements.txt`（或`environment.yml`）列出所需Python包，例如：  
   ```
   torch               # PyTorch (CPU或ROCm版)
   transformers        # HuggingFace 库
   vllm                # （可选）高效推理引擎
   tree-sitter         # AST解析
   pyyaml              # YAML处理
   deepdiff            # YAML差异比较
   fastapi             # 后端框架（如使用API服务器）
   uvicorn             # FastAPI运行
   ```
   AMD GPU时可在Dockerfile中通过额外索引安装ROCm版PyTorch【27†L117-L125】，例如：  
   ```dockerfile
   RUN pip install --upgrade pip && \
       pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/rocm5.4.1
   ```  
   若环境仅CPU，则直接`pip install torch`（CPU版即可）。  
2. **替换/扩展代码**：修改后端代码，将原`run_agent4`等API调用替换为本地模型推理函数。示例：  
   ```python
   from transformers import AutoTokenizer, AutoModelForCausalLM
   tokenizer = AutoTokenizer.from_pretrained("amd/AMD-Llama-135m")
   model = AutoModelForCausalLM.from_pretrained("amd/AMD-Llama-135m")
   input_ids = tokenizer(prompt, return_tensors="pt").input_ids
   outputs = model.generate(input_ids, max_new_tokens=200)
   review_text = tokenizer.decode(outputs[0], skip_special_tokens=True)
   ```  
   （如使用`run_agent4`前注入规则预命中，则可在调用LLM前后插入；或完全跳过LLM，仅使用规则引擎模式）。  
   对于大模型量化方案，可在CI脚本中先运行`convert-llama-weights`和`quantize`（如Soulteary所示【16†L109-L117】），然后在后端用llama.cpp运行二进制模型。  
3. **新增示例数据与模型文件**：在仓库中添加`data/`目录，存放示例Diff文件（如`example.patch`），用于演示功能。对于模型权重：  
   - **小模型内置**：可直接把`amd-llama-135m.safetensors`等小模型放入`models/`，确保无需下载即可推理。  
   - **自动下载**：对于较大模型，提供脚本`download_models.sh`，使用`wget`或`huggingface-cli`拉取公开权重。例如：  
     ```bash
     hf_hub_download --repo_id "amd/AMD-Llama-135m" --filename "pytorch_model.safetensors" --no_token
     ```  
     脚本需支持无交互运行，并验证文件完整性。  
4. **仓库结构示例**：  
   ```text
   ├── Dockerfile              # 构建环境（ROCm或CPU）
   ├── requirements.txt        # Python依赖
   ├── run.sh                  # 一键启动脚本（见下）
   ├── app/
   │   ├── main.py             # 后端主程序（FastAPI或CLI）
   │   ├── rules/              # YAML规则目录
   │   └── agents/             # 调度规则与LLM的逻辑
   ├── data/
   │   └── example.patch       # 示例Diff输入
   └── models/
       └── llama-135m.bin      # （可选）示例权重或小模型
   ```  
   **关键文件示例**：  
   - *Dockerfile*（ROCm GPU版）示例：  
     ```dockerfile
     FROM rocm/pytorch-training:v25.4
     WORKDIR /app
     COPY requirements.txt .
     RUN pip install --no-cache-dir -r requirements.txt
     COPY . .
     CMD ["bash", "run.sh"]
     ```  
   - *run.sh*（一键运行脚本）：  
     ```bash
     #!/bin/bash
     # 使用CPU模式运行示例
     uvicorn app.main:app --host 0.0.0.0 --port 8000
     # 或直接CLI模式: python app/main.py --input data/example.patch
     ```  
   以上结构确保克隆后只需执行`docker build .`或`bash run.sh`即可运行，不需额外配置。  
5. **模型权重策略**：若模型较大，可采用：  
   - **量化替代**：将模型量化后提供较小版本（参考Soulteary【16†L109-L117】）；  
   - **下载脚本**：提供自动下载（`download_models.sh`），确保在无GUI环境执行也可下载。引用Hugging Face API无需密钥即可获取公共模型。示例：  
     ```bash
     pip install huggingface_hub
     python -c "from huggingface_hub import hf_hub_download; hf_hub_download('amd/AMD-Llama-135m','pytorch_model.safetensors')"
     ```  
   对于无法网络下载的环境，可将小型模型文件附于仓库。  
6. **风险与兼容性**：  
   - **AMD/ROCm**：不同系统对ROCm支持有限，特别是Windows上PyTorch-ROCm支持不佳【27†L117-L125】。建议默认使用Linux；若评委使用Windows，可在`requirements.txt`中自动检测平台并选择CPU版PyTorch。Docker镜像使用ROCm可避免多平台配置问题【25†L229-L238】。  
   - **CPU性能**：在CPU上运行LLM很慢，需使用小型/量化模型。可在报告中声明：若无AMD GPU，则整体推理有限，仅做演示。  
   - **操作系统**：Docker方式可保证跨OS一致性；若不使用容器，需在文档中说明Windows/Linux的区别（如Docker或WSL）。  
   - **离线模式**：如环境禁网，则需提前将模型/依赖打包。我们提供两套方案（联网/离线），如题目要求。联网方案中使用脚本自动下载；离线方案则将必要文件嵌入仓库并禁用下载逻辑。  
   - **Fallback方案**：代码应检查是否有可用GPU（`torch.cuda.is_available()`），否则切换CPU模式；同时可提供环境变量切换，例如`USE_CPU=1 python run.sh`。

## 一键运行示例命令  
克隆仓库后，可使用以下命令直接运行（在线方案示例）：  
```bash
git clone <仓库地址> && cd <项目目录>
# 方案一：使用Docker（建议）
docker build -t rules-lm-engine . 
docker run --rm -it -p 8000:8000 rules-lm-engine
# 方案二：本地Python环境
pip install -r requirements.txt
# 若首次运行，下载示例模型和数据
bash download_models.sh
# 启动服务器（FastAPI）
uvicorn app.main:app --reload --host 0.0.0.0
```
运行后访问`http://localhost:8000/`即可看到示例审查结果。若仅需命令行示例，可执行：  
```bash
python app/main.py --input data/example.patch --mode rules_only
```
以上命令展示如何在纯CPU/AMD环境下一键运行，无需额外配置或API密钥。
